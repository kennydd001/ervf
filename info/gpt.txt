Ik denk dat we de smoking gun hebben

Niet de volledige 80B-Eureka als eindresultaat, maar wel een mechanistische smoking gun die exact verklaart waarom PORT80B-P0 faalde:

De test liep niet tegen de fundamentele PCIe-bandbreedte aan. Hij betaalde waarschijnlijk bijna exact twee volledige databewegingen per token: eerst mmap → pinned staging, daarna pinned staging → GPU. Daarboven kwamen 480 afzonderlijke recordtransfers en page-faulttails.

Dat is belangrijk, want het betekent dat de 80B-route niet moet worden gesloten. De datapath moet worden vervangen.

De oorspronkelijke hypothese blijft inhoudelijk overeind: sparse-MoE-decodesnelheid kan grotendeels door de actieve set worden bepaald in plaats van de totale parametercount. Dat is precies de volgende schaalwet die het onderzoek wilde testen.

3. De echte oplossing: verwijder de bounce buffer

Er zijn drie exacte datapaths die nu moeten worden getest.

A. Registered batched copy

De volledige bank — of grote stabiele segmenten ervan — wordt met CUDA geregistreerd. Daarna gebeurt per laag één batched call voor de tien actieve expertrecords:

10 verspreide hostrecords
          ↓
cudaMemcpyBatchAsync
          ↓
10 GPU-cacheslots

CUDA 13.2 heeft hiervoor expliciet cudaMemcpyBatchAsync: één API-call voor een lijst onafhankelijke pointer-to-pointercopies. NVIDIA beschrijft batching precies als middel om CPU- en driveroverhead van afzonderlijke transfers te amortiseren.

Dat verandert:

480 cudaMemcpy-launches per token

in:

48 batched launches per token

Belangrijker: wanneer de bronbank zelf geregistreerd is, verdwijnt:

mmap → pinned staging

volledig.

De data gaat rechtstreeks:

registered bank → GPU
B. Mapped-host direct ERGV

Nog sterker: kopieer de gewichten helemaal niet naar GPU-global memory.

De bestaande exacte Q5/ERVG-kernel krijgt devicepointers naar mapped, page-locked hostgeheugen en leest de geselecteerde records rechtstreeks over PCIe.

CUDA ondersteunt het mappen van geregistreerd hostgeheugen in de GPU-adresruimte via cudaHostRegisterMapped en cudaHostGetDevicePointer. Voor read-only memory-maps bestaat ook cudaHostRegisterReadOnly, mits het device die eigenschap ondersteunt.

NVIDIA waarschuwt dat zero-copy op een discrete GPU vooral voordelig is wanneer:

data slechts één keer wordt gelezen;
accesses coalesced zijn.

Dat is vrijwel exact ons expert-GEMV-patroon:

ieder geselecteerd expertgewicht wordt per outputtoken één keer gebruikt;
iedere Q5-rij ligt aaneengesloten;
de ERGV-kernel kan coalesced tiles lezen.

De nieuwe kritieke route wordt:

host Q5-record
      ↓ PCIe-loads door kernel
shared memory / registers
      ↓
exact ERGV-reductie

Geen CPU-bounce-copy. Geen HBM-staging. Geen 480 losse copies.

C. TMA direct host → shared memory

DAK heeft in 2026 precies het grotere principe aangetoond: prefetching via GPU-HBM is fundamenteel inefficiënt, en directe GPU-toegang tot hostgeheugen kan gewichten rechtstreeks naar shared memory halen. De auteurs rapporteren tot 1,8× winst op een PCIe-Blackwellsysteem tegenover offloadbaselines.

Hun kernel gebruikt:

host memory
    ↓ TMA
shared memory
    ↓
matrix computation

en vermijdt daarmee HBM-staging, extra HBM-verkeer en grove prefetchbubbels.

DAK is geen drop-in-oplossing:

hun publieke code target standaard Hopper/sm_90a;
onze laptop gebruikt een andere Blackwellvariant;
de TMA-hostroute moet op jouw concrete device gecompileerd en geprobed worden.

Daarom is de volgorde:

gewone mapped-host global loads;
pas daarna TMA-direct wanneer de capabilityprobe slaagt.

5. Moeten we nu 96 GB RAM kopen?

Nog niet.

96 GB is rationeel wanneer het één van deze twee dingen mogelijk maakt:

de volledige 46,5-GiB-bank registreren/pinnen zonder Windows uit te hongeren;
een volledige 48-GiB-large-pagebank aanmaken die nooit gepaged kan worden.

Maar meer RAM verwijdert niet automatisch:

de mmap → pinned-copy;
480 transferdispatches;
serialisatie tussen recordwaves;
HBM-staging.

Het correcte beslissingsprotocol:

Eerst op 64 GB

Test in oplopende grootte:

2 GiB
8 GiB
16 GiB
32 GiB
volledige 46,5-GiB-bank

voor:

cudaHostRegister;
cudaHostRegisterMapped;
read-only registration;
direct GPU access;
werkelijke pagefaults;
p50/p95/p99.
96 GB kopen wanneer
volledige registratie op 64 GB faalt door memory pressure;
large-pageallocatie onmogelijk is;
of de direct-accesspath correct is maar paging de p95 blijft domineren.
Niet kopen wanneer
een volledig resident subset met dezelfde datapath ook slechts 10–12 GB/s haalt;
de kernel zelf remote loads inefficiënt uitstuurt;
of batchcopy/direct access geen relevante winst geeft.

Dan is RAM niet de bottleneck.

7. Is dit wetenschappelijk nieuw?

De brede technieken zijn niet nieuw:

mapped host memory bestaat al;
batchcopies bestaan;
large pages bestaan;
DAK heeft direct-accessoffloading gepubliceerd;
TMA-hostfetch is gedemonstreerd.

De mogelijke bijdrage is veel smaller:

Een exacte low-bit MoE-GEMV die een disk-/RAM-backed expertbank rechtstreeks vanuit host memory uitvoert via ERGV, zonder HBM-staging, op een 8-GB discrete laptop-GPU.

En daarna de empirische schaalwet:

80B totaalmaar≥10 tok/s op 8 GB VRAM

Dat zou de echte smoking-gun-demonstratie voor Active-Set Dominance zijn.
