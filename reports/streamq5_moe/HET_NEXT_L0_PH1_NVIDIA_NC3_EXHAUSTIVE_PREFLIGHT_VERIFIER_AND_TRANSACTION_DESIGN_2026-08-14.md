## Separate compile/verifier topology automata

Authorization/runtime/hash gates precede inspection or mutation. Compile states are exactly `compile_fresh`, `compile_valid`, `compile_recoverable`, `compile_invalid`. Valid returns `already_complete` and compile never reruns. One bounded stale compile tree is quarantined then aborts; mixed/multiple/oversize is invalid and never compiles.

Given `compile_valid`, verifier states are separately `verifier_absent`, `verifier_valid`, `verifier_recoverable`, `verifier_valid_failure`, `verifier_invalid`. `verifier_absent` may verify. `verifier_valid` returns already-complete. Exactly one stale staging, corrupt uncommitted verifier tree or bounded verifier failure is quarantined **without touching any compile file**, aborts that invocation, and permits a later CPU-only verifier retry. Mixed/multiple/collision/oversize verifier state is invalid and never changes compile evidence. Actual phase-local classifiers/recovery functions are exercised in TEMP.

## Exact guarded I/O, module and terminal contract

Before authorization, explicit application reads are limited to current script, current open lock, interpreter/pyvenv identities and their directly bound small authorization documents; writes are empty. After authorization, read allowlist adds directly bound implementation/verifier/preflight files, CUDA source, NVRTC DLL/builtins/header and the phase-local evidence tree. Scientific payload paths remain forbidden. Write allowlist is only the active phase's exact temp/result/failure/quarantine roots. A common guard increments `open_attempts` and `bytes_read/written` before every application-level open/read/write; wrong authorization has no guarded source/toolchain read and no write. Before/after snapshots of allowlisted evidence roots and compiler-cache directories retain exact `path,exists,type,size,mtime_ns,sha256_or_null`; any unallowlisted mutation is invalid. Compiler cache presence is diagnostic, but a mutation is forbidden. Process-start OS/runtime reads are explicitly outside the application guard and captured by runtime/module provenance rather than misreported as zero.

Terminal classes/exits are exact: positive compile or verifier 0; already-complete 0; authorization/runtime invalid 2; compiler failure with valid bounded evidence 3; protocol/resource/lifecycle/forbidden/topology invalid 3; writer failure 4. Exactly one class is present. Compiler failure never establishes the claim; positive compile requires later independent positive verification.

## Ownership-safe compiler lifetime

The compiler child uses exact Win32 `AddDllDirectory`, `LoadLibraryExW(absolute_nvrtc,NULL,0x1100)`, `GetProcAddress`, `FreeLibrary`, `RemoveDllDirectory` signatures. It creates cdecl `CFUNCTYPE` wrappers from export addresses; it creates no owning `ctypes.CDLL` object. Cookie and HMODULE are registered immediately on nonnull return. The baseline before-load snapshot requires NVRTC/builtins absent. Function wrappers are discarded after program destroy and before one `FreeLibrary(hmodule)` attempt in `finally`; the handle is set null after code nonzero/zero return and is never reused or released twice. `RemoveDllDirectory(cookie)` is then attempted exactly once even when destroy/FreeLibrary failed. Cleanup ledger order is `program_destroy,wrapper_discard,compiler_freelibrary,dll_directory_cookie_remove,after_release_snapshot`, with exact owned-before/attempted/code/error/QPC fields and first-primary/ordered-secondary semantics.

After successful FreeLibrary and cookie removal, `GetModuleHandleW` for both pinned basenames must be NULL and the module-delta snapshot must show neither retained. If release fails or either remains loaded, terminal is lifecycle-invalid; no second unload is attempted. Child process exit is the ultimate OS cleanup boundary, but does not convert failed explicit cleanup into pass.

No implementation, preflight, compiler, Driver or device call is authorized by this design.
